# MILESTONES – מערכת ניהול הוצאות

**מסמכי מקור:** `PRD.md`, `ARCHITECTURE.md`, `DESIGN.md`  
**ממשק המשתמש:** עברית, RTL, מותאם ל-Desktop ול-Mobile.  
**עקרון החלוקה:** Vertical Slices שניתן להריץ ולבדוק בנפרד, ולא חלוקה מלאכותית לפי Frontend / Backend / Database. אין כאן הערכות זמנים.

> **מגבלת מוצר מהותית:** בהתאם ל-PRD אין Authentication או הפרדת משתמשים. הוצאות נשמרות במסד משותף, ולכן כל מי שיכול להגיע ל-API הציבורי עשוי לקרוא ולשנות אותן. אין להזין נתונים פרטיים או רגישים לצורך הדגמה, ואין להציג את המערכת כמאובטחת לשימוש אישי פרטי. לא להוסיף Authentication ללא שינוי מאושר ב-PRD.

## Milestone 1 – יסודות הפרויקט ורישום הוצאה מקצה לקצה ✅

**מטרה:** להקים סביבת עבודה וסביבות Cloud נפרדות, ולהוכיח את שרשרת הפעולה Browser → Backend → Database באמצעות הוספת הוצאה וצפייה בה.

**מה יש לממש:**
- יצירת Git Repository ב-GitHub עם יישום React + TypeScript + Vite, תצורת Vercel Functions, תלויות הפרויקט, בדיקות בסיסיות והגדרות סביבה ללא סודות ב-Git.
- **הקמה בהדרכת AI צעד אחר צעד, על ידי המשתמש:**
  1. המשתמש פותח חשבון/נכנס ל-Supabase ויוצר **שני פרויקטים נפרדים בענן**, אחד ל-Development ואחד ל-Production; מוודא איזה מהם הוא כל אחד. אין צורך בהתקנת Docker או בהרצת Supabase מקומי.
  2. המשתמש יוצר/מחבר פרויקט Vercel ל-GitHub לצורך פיתוח ופריסה עתידית, בהנחיית ה-AI. יש למנוע Production Deployment אוטומטי ומתחרה ישירות מ-Vercel, כי בהמשך GitHub Actions יהיה מנהל הפריסה היחיד.
  3. המשתמש שומר פרטי גישה ל-**Development בלבד** ב-`.env.local` שאינו עולה ל-Git, או במשתני סביבת Development/Preview של Vercel. **פרטי Production אינם נשמרים במחשב המקומי או ב-Frontend**; בשלב המתאים הם יוגדרו בסודות Production של Vercel וב-GitHub Actions לצורך Migrations.
  4. ה-AI מדריך בכל מסך הגדרות בנפרד, מסביר כיצד למצוא Project URL ופרטי גישה, ומבקש מהמשתמש להזין סודות **ישירות בממשקי השירותים**, לא להדביק אותם בשיחה או ב-Repository.
- כתיבת Migration ראשונה לטבלת `public.expenses` לפי ה-ARCHITECTURE: UUID, קטגוריה מאושרת, תיאור, סכום באגורות, תאריך הוצאה, חותמות זמן, Constraints ו-Index; הגדרת RLS/הרשאות גישה בהתאם לארכיטקטורה. **הרצת Migration על Development בלבד.**
- מימוש חלק מה-Dashboard המשותף ומסך הבית: טופס יצירת הוצאה עם כל כללי הוולידציה, `POST /api/expenses`, `GET /api/expenses`, הצגת הוצאות שנשמרו והודעות טעינה/שגיאה מתאימות. שמירה מוצלחת מוצגת רק לאחר אישור ה-Backend.
- בסיס חזותי עקבי על פי `DESIGN.md`: עברית RTL, Palette, Typography ו-Layout רספונסיבי; אין צורך להשלים עדיין את יתר הדפים.

**תוצר מצופה:** אפשר לפתוח את האתר בסביבת Development, לרשום הוצאה תקינה, לשמור אותה ב-Supabase Development ולראות אותה שוב לאחר Reload.

**Definition of Done:**
- [ ] שני פרויקטי Supabase נוצרו ונבדלו בבירור; הפעולות במהלך הפיתוח פונות ל-Development בלבד.
- [ ] ה-Migration הראשונה נשמרה ב-Git והורצה בהצלחה ב-Development; הטבלה, האילוצים וההרשאות קיימים ונבדקו.
- [ ] אפשר ליצור הוצאה עם אחת מ-11 הקטגוריות, תאריך היום כברירת מחדל, תיאור אופציונלי למעט ב-"אחר", וסכום בשקלים בדיוק של עד שתי ספרות.
- [ ] Frontend ו-Backend דוחים קלט שגוי (שדה חובה, "אחר" ללא תיאור, סכום לא חוקי/מעל ₪100,000, תאריך עתידי).
- [ ] הנתונים נשלפים מה-API ונשארים לאחר Reload; כשל API אינו מוצג כאפס הוצאות או כהצלחת שמירה.
- [ ] אין Secrets בקוד, ב-Commit או ב-Bundle הדפדפן; קריאה ישירה בלתי מורשית לטבלה אינה מאפשרת גישה לנתונים.
- [ ] בדיקות רלוונטיות ו-Build של המימוש הנוכחי עוברים; תוצאת בדיקה ידנית מוצגת למשתמש.

## Milestone 2 – השלמת ניהול ההוצאות בדף הבית ✅

**מטרה:** להפוך את דף הבית לכלי CRUD מלא ומעוצב, שימושי גם במחשב וגם בטלפון.

**מה יש לממש:**
- `PUT /api/expenses/:id` ו-`DELETE /api/expenses/:id`, עם ולידציה בצד שרת, טיפול ברשומה שאינה קיימת ותגובות שגיאה עקביות.
- לחצן **"עדכון"** הפותח Modal מאוכלס בפרטי ההוצאה; שמירה לאחר ולידציה ועדכון התצוגה רק לאחר אישור מה-API.
- לחצן **"מחיקה"** המציג Dialog אישור; ביטול משאיר את הנתונים ללא שינוי.
- טבלת הבית עם מיון אינטראקטיבי לפי תאריך, קטגוריה וסכום, ברירת מחדל תאריך מהחדש לישן; תצוגה נוחה וקריאה ב-Mobile.
- השלמת עיצוב דף הבית בהתאם ל-Wireframes, ל-Style Guide ול-Mockups; טיפול ברשימה ריקה ובכשלי רשת/שמירה.

**תוצר מצופה:** דף בית מלא המאפשר להוסיף, לצפות, לעדכן, למחוק ולמיין הוצאות מול Database ה-Development.

**Definition of Done:**
- [ ] עדכון תקין נשמר ומופיע אחרי Reload; עדכון שגוי אינו נשמר וה-Modal מאפשר תיקון.
- [ ] מחיקה מתבצעת רק לאחר אישור; ביטול אינו משנה נתונים.
- [ ] הוצאה שאינה קיימת מטופלת כראוי ללא הודעת הצלחה מטעה.
- [ ] מיון בכל שלוש העמודות עובד; מיון ברירת המחדל נכון.
- [ ] מצב ריק וכשל טעינה/שמירה מוצגים באופן מובחן וברור בעברית.
- [ ] המסך נבדק על Desktop ועל Mobile, בעיצוב כהה וב-RTL; בדיקות CRUD/Validation רלוונטיות עוברות.
- [ ] לא בוצעו שינויים ב-Production. אם התווספה Migration, היא נשמרה ב-Git והורצה ונבדקה ב-Development בלבד.

## Milestone 3 – סינון ומיון הוצאות

**מטרה:** לאפשר איתור הוצאות לפי תאריך וסכום, ללא פגיעה ברשימת דף הבית.

**מה יש לממש:**
- דף **"פילטרים"** עם בחירת שנה, חודש לאחר שנה, יום לאחר חודש וסכום מקסימלי בשקלים; שילוב תנאים באמצעות AND.
- התחשבות במספר הימים בחודש ובשנה מעוברת, ואיפוס/עדכון בחירות תלויות כששנה או חודש משתנים.
- כפתורי **"הצג תוצאות"** ו-**"איפוס סינון"**, וטבלת תוצאות עצמאית עם מיון לפי תאריך, קטגוריה וסכום; ברירת מחדל תאריך יורד.
- תצוגת "אין תוצאות" והבחנה בינה לבין כשל שליפת נתונים; עיצוב רספונסיבי לפי `DESIGN.md`.

**תוצר מצופה:** דף פילטרים עובד שאפשר להפעיל בנפרד ולשלב בו סינונים, בלי להשפיע על טבלת הבית.

**Definition of Done:**
- [ ] סינון לפי שנה, שנה+חודש, שנה+חודש+יום, סכום מקסימלי, ושילוב תאריך+סכום מחזיר רק התאמות נכונות.
- [ ] גבולות התאריך וסכום השווה לתקרה מטופלים נכון; שינוי בחירת הורה אינו משאיר בחירת ילד בלתי חוקית.
- [ ] איפוס מחזיר את ברירות המחדל; מיון עמודות פועל ללא תלות בטבלת הבית.
- [ ] כשאין התאמות מופיעה הודעה מתאימה, ולא טבלה ריקה מבלבלת.
- [ ] המסך וניווט אליו עובדים ב-Desktop וב-Mobile, בעברית RTL; בדיקות הסינון והמיון עוברות.
- [ ] אין שינוי ב-Production; כל Migration חדשה, אם נדרשה, הורצה ונבדקה ב-Development בלבד.

## Milestone 4 – דו"חות וגרפים

**מטרה:** לתת למשתמש תמונה גרפית נכונה של הוצאותיו, על בסיס כלל הנתונים השמורים.

**מה יש לממש:**
- דף **"דו"חות"** עם Pie לפי קטגוריות שיש עבורן הוצאות, וגרף עמודות אחד עם מעבר בין שנים לחודשים; בבחירה חודשית ניתן לבחור שנה.
- בחירת מדד משותפת: **"סכום בשקלים"** או **"מספר הוצאות"**; חישוב אגרגציות עקבי, על בסיס סכומים באגורות שלמות.
- גרפים, מקרא, תוויות ותצוגות ריקות בהתאם ל-`DESIGN.md`; פריסה לצד-לצד ב-Desktop ואנכית ב-Mobile.
- הבטחת עצמאות הגרפים מפילטרים שבדף הפילטרים (ומפילטרי הייצוא שימומשו בהמשך).

**תוצר מצופה:** דף דו"חות עם שני גרפים אינטראקטיביים המייצגים נכונה את כלל ההוצאות.

**Definition of Done:**
- [ ] Pie כולל רק קטגוריות עם הוצאות; הסכומים/הכמויות תואמים לנתוני המקור.
- [ ] גרף העמודות מציג שנים או חודשים בשנה שנבחרה, לפי בחירת המשתמש.
- [ ] מעבר בין סכומים לכמות מעדכן את שני הגרפים ללא שגיאות עיגול כספי.
- [ ] פילטרים בדף הפילטרים אינם משנים את הגרפים.
- [ ] כשאין הוצאות מופיעה הודעה מתאימה במקום תרשים ריק; Desktop ו-Mobile קריאים ב-RTL.
- [ ] בדיקות חישובי הגרפים וה-Build עוברים; אין שינוי ב-Production, וכל Migration חדשה (אם קיימת) נבדקה ב-Development בלבד.

## Milestone 5 – ייצוא קבצים ודף האודות

**מטרה:** להשלים את חוויית המשתמש באמצעות הורדת נתונים ועמוד מידע, תוך שמירה על עצמאות הגרפים.

**מה יש לממש:**
- בדף הדו"חות: בחירת **"כל ההוצאות"** או **"הוצאות מסוננות"**, פילטרי ייצוא עצמאיים לפי שנה, חודש, יום וסכום מקסימלי, ולחצני **"הורדת CSV"** ו-**"הורדת PDF"**.
- יצירת CSV עם כותרות ונתוני ההוצאה בעברית, קידוד UTF-8 המתאים לפתיחה ב-Excel, והגנה על ערכי טקסט מפני CSV Formula Injection.
- יצירת PDF ברור ומעוצב עם Font עברי, RTL, תאריכים וסכומים קריאים, והורדה למכשיר; שני הפורמטים מכילים רק את ההוצאות שנבחרו.
- הודעת "אין הוצאות מתאימות לייצוא" במקום הורדת קובץ ריק מטעה.
- דף **"אודות"** עם הסבר על המערכת, מקום לתיאור התלמיד/ה ולתמונתו/ה כפי שהוגדר ב-PRD; ללא המצאת פרטים אישיים. השלמת הניווט והעקביות החזותית בארבעת הדפים לפי `DESIGN.md`.

**תוצר מצופה:** ארבעת דפי המוצר עובדים ב-Development; אפשר להפיק קובצי CSV ו-PDF בעברית מתוך כלל ההוצאות או מתוך הוצאות מסוננות.

**Definition of Done:**
- [ ] בחירה בייצוא כל ההוצאות ובייצוא מסונן מפיקה את הרשומות הנכונות בכל פורמט.
- [ ] פילטרי הייצוא עצמאיים מפילטרי דף הפילטרים ואינם משנים את גרפי הדו"חות.
- [ ] CSV נפתח עם עברית ועמודות תקינות; טקסטים מסוכנים אינם מבוצעים כנוסחאות.
- [ ] PDF נפתח, קריא ב-RTL, מציג סכומים/תאריכים וטקסט עברי בסדר תקין.
- [ ] היעדר התאמות לייצוא מוביל להודעה ולא להורדה מטעה.
- [ ] דף האודות מכיל את המבנה והתוכן שהוגדרו; תמונה ותיאור אישיים ימולאו רק מפרטים שסופקו בפועל.
- [ ] כל ארבעת הדפים וניווט ביניהם נבדקו ב-Desktop וב-Mobile; בדיקות ייצוא ו-Build עוברים.
- [ ] כל Migration חדשה, אם נדרשה, הורצה ונבדקה ב-Development בלבד; Production עדיין לא עודכן.

## Milestone 6 – פריסה אוטומטית מבוקרת ל-Production

**מטרה:** לפרסם את המערכת המלאה ב-Vercel עם Supabase Production, תוך שמירת סדר בטוח של בדיקות → Database Migrations → Deployment.

**מה יש לממש:**
- הגדרת סודות **Production בלבד** בסביבת Production של Vercel וב-GitHub Actions לפי צורכי הפריסה, באמצעות הזנה על ידי המשתמש ישירות בממשקי השירותים ובהדרכת AI צעד אחר צעד; אין העתקת סודות Production למחשב המקומי או ל-Frontend.
- Pipeline יחיד ב-GitHub Actions: בדיקות ו-Build, בדיקת Migrations שכבר הורצו על Supabase Development, החלת Migrations ממתינות על Supabase Production, ורק לאחר הצלחתן פריסת Frontend ו-Backend ל-Vercel Production.
- מניעת פריסה מתחרה: לא לאפשר Auto-Deploy עצמאי מ-Vercel על `main` במקביל ל-Pipeline; לא להפעיל מסלול נוסף המחיל אותן Migrations ב-Supabase. הגבלת פריסות Production מקבילות.
- הגדרת ניתוב ל-React Router ול-`/api/*`, משתני סביבה מתאימים, בדיקות סודות/RLS ו-Smoke Tests של ארבעת הדפים ופעולות הליבה מול Production עם **נתוני דמו לא רגישים בלבד**.
- לאחר אישור מפורש של המשתמש למיזוג/Push ל-`main`, הפעלת הפריסה האוטומטית; יש לבצע בקרה על Migration לפני פריסה, ולעצור אוטומטית אם היא נכשלת. אין להעתיק את נתוני Development ל-Production.

**תוצר מצופה:** אתר Production נגיש ב-Vercel ומחובר ל-Supabase Production; שינוי מאושר המגיע ל-`main` מפעיל פריסה אוטומטית מסודרת ללא צעדי פריסה ידניים חוזרים.

**Definition of Done:**
- [ ] פרטי Development ו-Production מופרדים; אין Production Secrets ב-Repository, בדפדפן או במחשב הפיתוח.
- [ ] כל ה-Migrations הוחלו תחילה ונבדקו ב-Development; לאחר אישור המשתמש הן הוחלו בהצלחה ב-Production **לפני** פריסת הקוד התלוי בהן.
- [ ] Push/Merge מאושר ל-`main` מפעיל GitHub Actions ופורס ל-Vercel ללא פריסה עצמאית מתחרה; כשל Migration מונע פריסת גרסה חדשה.
- [ ] ארבעת הדפים, נתיבי API ורענון דף פנימי עובדים ב-Production על Desktop וב-Mobile.
- [ ] הוספה, קריאה, עדכון ומחיקה מול Supabase Production, גרפים וסינון וייצוא CSV/PDF נבדקו על **נתוני דמו בלבד**.
- [ ] לא קיימת גישה ישירה בלתי מורשית לטבלת Supabase באמצעות מפתח ציבורי; Secret נשמר רק בצד שרת. המגבלה של API ציבורי ללא Authentication הובהרה למשתמש.
- [ ] תוצאות ה-CI ובדיקות ה-Smoke מוצגות למשתמש; אין להצהיר על השלמת Milestone אם פריסה או בדיקה נכשלו.

## Development Execution Rules – הנחיות מחייבות ל-AI המפתח

1. **יש לפתח את ה-Milestones בסדר שבו הם מופיעים במסמך.** בכל Milestone מותר להשתמש רק בתשתית וביכולות שמומשו באבני דרך קודמות ולהוסיף את הנדרש לאותה אבן דרך; אין להתחיל יכולות של Milestone עתידי מראש.
2. **בסיום כל Milestone יש לעצור.** הצג למשתמש את מה שנבנה, כיצד ניתן להפעיל ולבדוק אותו, ואת תוצאות הבדיקות בפועל כנגד כל סעיף ב-Definition of Done. יש לציין במפורש תנאים שלא הושלמו או בדיקות שלא ניתן היה לבצע; אין לסמן אותם כעברו.
3. **אין להתחיל בפיתוח ה-Milestone הבא ללא אישור מפורש של המשתמש.** עצירה זו חלה גם אם כל הבדיקות עברו, ואין לראות במעבר אוטומטי בין משימות כאישור.
4. לפני כל פעולה הדורשת יצירת חשבון, פרויקט Cloud, הרשאה או הזנת Secret, יש להדריך את המשתמש **שלב אחר שלב**, בשפה פשוטה. אין לבקש להדביק Secrets בשיחה או לתעד אותם בקוד.
5. כל שינוי בסכמת Database מתועד בקובץ Migration ונבדק **קודם** בפרויקט Supabase Development; אין להריץ Migration ידנית על Production במסגרת Milestones 1–5. ב-Milestone 6, ורק לאחר אישור המשתמש לפרסום, ה-Pipeline מחיל Migrations ב-Production לפני הקוד החדש. לאחר הפרסום, כל שינוי עתידי כפוף לאותו כלל ואישור של המשתמש.
6. `PRD.md` קובע את הפונקציונליות, `ARCHITECTURE.md` קובע את אופן המימוש הטכני, ו-`DESIGN.md` קובע את המבנה והשפה החזותית. במקרה של אי-התאמה, אין להמציא דרישה חדשה; יש להצביע על הסתירה ולפעול לפי המסמך המוסמך לאותו נושא.
