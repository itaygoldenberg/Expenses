## 3. ארכיטקטורת התחברות (Authentication Architecture)

### העיקרון
**Supabase Auth** מחזיק את הסיסמאות, האימיילים וה-Sessions (אין שמירת סיסמאות אצלנו). אנחנו מוסיפים רק מיפוי מאובטח **שם משתמש → חשבון** בצד השרת.

### זרימות
- **הרשמה** — `POST /api/auth/register {username, email, password}`:
  ולידציה (שם משתמש: 3–20 תווים, אותיות/ספרות/קו תחתון, בלי הבחנה בין גדולות לקטנות; סיסמה: לפחות 10 תווים + בדיקה מול רשימת סיסמאות נפוצות של Supabase) → השרת קורא ל-Supabase Auth `signUp` עם שם המשתמש ב-metadata → **Trigger במסד** יוצר שורה ב-`profiles` עם אילוץ UNIQUE על שם המשתמש (atomic — אין "מרוץ" בין שני נרשמים לאותו שם). אם השם תפוס — "שם המשתמש כבר בשימוש" (חשיפה מקובלת ומכוונת: אי אפשר לבחור שם בלי לדעת שהוא תפוס). אימייל תפוס **לא** נחשף — Supabase מחזיר תשובה זהה ושולח מייל לבעלים.
- **התחברות** — `POST /api/auth/login {username, password}`:
  השרת מאתר את ה-user לפי שם המשתמש **בתוך המסד** (האימייל לעולם לא חוזר לדפדפן) → מבצע `signInWithPassword` מול Supabase Auth בצד השרת → מחזיר לדפדפן רק את ה-Session (access + refresh token). **תשובה זהה** "שם משתמש או סיסמה שגויים" — גם כשהשם לא קיים וגם כשהסיסמה שגויה, ובזמן תגובה דומה (מניעת User Enumeration).
- **שחזור סיסמה** — לפי שם משתמש או אימייל → תמיד "אם החשבון קיים, נשלח מייל" → קישור של Supabase → מסך "סיסמה חדשה".
- **התנתקות** — `signOut` (מבטל את ה-refresh token).
- **Session** — supabase-js בדפדפן שומר ומחדש את ה-Session. כל קריאה ל-API שולחת `Authorization: Bearer <access token>`. **השרת מאמת את ה-JWT בעצמו** מול מפתחות הציבור של Supabase (JWKS, חתימה אסימטרית) — ומשם בלבד לוקח את ה-`user_id`. כל `user_id` שמגיע מהדפדפן מתעלמים ממנו.
- **Session שפג** → ניסיון חידוש אוטומטי; אם נכשל → מעבר למסך ההתחברות עם הודעה.
- **CSRF:** הזהות עוברת בכותרת Authorization ולא ב-Cookie, ולכן CSRF קלאסי לא רלוונטי. מנגד, טוקן ב-localStorage חשוף ל-XSS — לכן יתווסף Content-Security-Policy קפדני, ואין שימוש ב-`innerHTML`.

### הגנות
- **Rate limiting משלנו במסד:** טבלה `auth_attempts` (hash של שם המשתמש + hash של כתובת ה-IP, חלון זמן). לדוגמה: עד 5 כישלונות לשם משתמש ב-15 דקות, עד 20 ל-IP. נדרש כי **כל** קריאות ההתחברות מגיעות ל-Supabase מאותה כתובת של Vercel, כך שהגבלת ה-IP המובנית של Supabase לא מבחינה בין משתמשים (וגרוע מזה — תוקף אחד יכול לחסום את כולם). זו נקודה שצריך לאמת בבנייה.
- אין רישום סיסמאות, טוקנים או אימיילים בלוגים (כבר היום הלוגים רושמים רק קוד שגיאה).
- כל ה-API (חוץ מהרשמה/התחברות/שחזור) דורש Session תקף → `401` בלי.

### דרוש ממך (חשבונות / הגדרות)
- **שליחת מיילים (אימות הרשמה + שחזור סיסמה):** שירות המייל המובנה של Supabase **שולח רק לכתובות של חברי הצוות בפרויקט** ובמכסה זעירה. לשימוש אמיתי צריך SMTP חיצוני (למשל Resend, יש תוכנית חינמית) — חשבון שאתה פותח, בהדרכה. ראו החלטה 2.
- הגדרות Auth בשני פרויקטי Supabase (Site URL, תבניות מייל בעברית, אורך סיסמה) — בהדרכה.

## 4. ארכיטקטורת מסד הנתונים (Database Architecture)

### שינויי מבנה (Migrations חדשות, Backward-compatible)
| טבלה | תוכן |
|------|------|
| **`profiles`** (חדש) | `user_id` (PK, מפנה ל-`auth.users`, ON DELETE CASCADE), `username` (citext UNIQUE), `display_name`, `created_at`. נוצר ב-Trigger בהרשמה. |
| **`expenses`** (הרחבה) | `user_id uuid NOT NULL` (מפנה ל-`auth.users`), `source` ('manual' / 'import'), `import_id` (nullable), שדות מהדוח: `merchant`, `posting_date`, `original_amount` + `original_currency`, `installment_number` + `installments_total`, `external_ref`, `fingerprint` (לזיהוי כפילויות), ו-`kind` אם יאושרו הכנסות/זיכויים (החלטה 3). אינדקס `(user_id, expense_date desc)`. |
| **`imports`** (חדש) | `id`, `user_id`, `file_name` (מנוקה), `file_hash` (SHA-256 — לזיהוי העלאה חוזרת של אותו קובץ), `source_kind` ('bank' / 'card'), `format` ('csv' / 'xlsx' / 'pdf'), `status`, מונים (זוהו / יובאו / נדחו / כפולים), `period_from/to`, `created_at`. **ללא הקובץ עצמו.** |
| **`auth_attempts`** (חדש) | ל-Rate limiting (סעיף 3). ללא פרטים מזהים גלויים (hashes בלבד), נמחק אוטומטית אחרי 24 שעות. |
| **קטגוריות** | נשארות רשימה קבועה (11 הקיימות) — לא הוספתי טבלה. כללי סיווג אוטומטי בקוד (שלב G). טבלת "כללים אישיים" רק אם תאושר בהמשך. |

### מנגנון ההרשאות (הנקודה הכי חשובה)
היום ה-Backend מתחבר ישירות ל-PostgreSQL, ו-**RLS לא "יודע" מי המשתמש** בחיבור כזה. ההצעה (**אפשרות א', מומלצת**) — "RLS אמיתי דרך חיבור ישיר":
1. בכל בקשה, השרת מאמת את ה-JWT ופותח טרנזקציה:
   `SET LOCAL ROLE authenticated;` + `set_config('request.jwt.claims', '<claims מאומתים>', true)`.
2. ה-Policies בכל טבלה: `using (user_id = auth.uid())` ו-`with check (user_id = auth.uid())` — ל-SELECT, INSERT, UPDATE, DELETE.
3. `app_backend` **מאבד** את הגישה הישירה לטבלאות (מבוטלים ה-GRANT וה-Policy הנוכחיים) ויכול רק "להתחפש" ל-`authenticated` בתוך טרנזקציה. כך גם באג בקוד השרת (למשל שכחת `where user_id`) **לא** יחשוף נתונים של משתמש אחר — המסד יחסום.
4. בנוסף (הגנה כפולה) — כל שאילתה בשרת מסננת גם לפי `user_id` מהטוקן.
5. ה-Data API נשאר כבוי.
- **אפשרות ב':** להדליק את ה-Data API ולעבור ל-supabase-js בדפדפן עם RLS. מוכר ופשוט ב-Supabase, אבל משכתב את כל שכבת ה-API שבנינו ומבטל את ADR-1.
- **אפשרות ג':** סינון בקוד השרת בלבד, בלי RLS. פשוט — אבל לא עומד בדרישה ש"ההרשאות ייאכפו גם במסד".
- **בדיקות חובה (Milestone E):** שני משתמשי בדיקה; בדיקות SQL ישירות במסד (בתור כל אחד מהם) ובדיקות API — קריאה, עדכון, מחיקה וייצוא של רשומה של השני חסומים, החלפת IDs לא עוזרת, בקשה בלי טוקן נדחית.

### שיוך הנתונים הקיימים
- **Development:** כ-10 רשומות — כולן נתוני בדיקה שיצרנו (ועוד "SADAS" שהוספת). **Production:** אין טבלה ואין נתונים.
- תוכנית: (1) Migration מוסיפה `user_id` כ-**nullable** (לא שובר כלום); (2) אתה נרשם ב-Development; (3) אני מראה לך את רשימת הרשומות ואת ה-`user_id` שלך, ורק באישורך משייך אותן אליך ב-UPDATE אחד; (4) Migration שנייה הופכת את `user_id` ל-NOT NULL. **שום רשומה לא נמחקת.** כל Migration עם תסריט ביטול (rollback) כתוב.
- ב-Production הטבלאות ייווצרו מראש במבנה החדש.

## 5. ארכיטקטורת ייבוא דוחות (Bank Statement Import Architecture)

### העיקרון: **הקובץ לא עוזב את המכשיר**
הפענוח נעשה **בדפדפן**. לשרת נשלחות רק העסקאות שהמשתמש אישר, כ-JSON מנורמל. יתרונות: פרטיות (אין אחסון של דוחות, אין קבצים בלוגים, אין צד שלישי), בלי מגבלת 4.5MB לבקשה ב-Vercel ובלי זמני עיבוד בשרת. השרת עדיין מאמת כל שורה (Zod) ומבצע בדיקת כפילויות מול המסד.

### שלבים
1. **העלאה:** גרירה / בחירה, עד 10MB. בדיקת סוג אמיתי לפי "חתימת קובץ" (`PK` ל-XLSX, `%PDF` ל-PDF, טקסט ל-CSV) ולא רק סיומת. שם הקובץ נשמר רק כטקסט מנוקה.
2. **פענוח:**
   - **CSV:** Papa Parse (כבר מותקן). זיהוי קידוד: UTF-8 (עם/בלי BOM) ו-**Windows-1255** (נפוץ בייצוא מבנקים בישראל) — דרך `TextDecoder`.
   - **XLSX:** **SheetJS** מההפצה הרשמית (`cdn.sheetjs.com` — הגרסה ב-npm ישנה ופגיעה). קריאת גיליון, מציאת שורת הכותרות (דוחות ישראליים מתחילים בשורות מידע לפני הטבלה).
   - **PDF:** **pdf.js** — חילוץ טקסט עם מיקומים ושחזור שורות/עמודות. **רק PDF טקסטואלי.** PDF סרוק → הודעה "הקובץ סרוק ולא ניתן לקרוא אותו; נסה להוריד מהבנק CSV/Excel". PDF מוגן בסיסמה → הודעה מתאימה.
3. **זיהוי עמודות:** מילון כותרות בעברית ובאנגלית (למשל: "תאריך עסקה", "תאריך רכישה", "תאריך חיוב", "שם בית העסק", "תיאור", "סכום עסקה", "סכום חיוב", "מטבע", "פרטים", "תשלום X מתוך Y"…) + **התאמה ידנית** כשהזיהוי לא בטוח. פרופילים למבנים נפוצים (ישראכרט/אמריקן אקספרס, מקס, כאל, בנקים) — **רק לפי דוגמאות מבנה שתספק** (כותרות בלבד, בלי נתונים אמיתיים), כי אין לי דוחות אמיתיים ואסור להמציא.
4. **נרמול:** תאריכים (`DD/MM/YYYY`, `DD.MM.YY`, `DD-MM-YYYY`, ערכי תאריך של Excel), סכומים (מפרידי אלפים, `₪`, מינוס בהתחלה או בסוף, סוגריים), זיכויים, תשלומים ("3 מתוך 12"), מטבע זר. **כל שדה מסומן "מהדוח" או "הוסק"** — ושום ערך חסר לא מומצא.
5. **תצוגה מקדימה (לפני כל שמירה):** כמה עסקאות זוהו, סכומים לפי סוג ומטבע, טווח תאריכים, מקור; רשימה עם סימון "חסר שדה" / "דורש תיקון" / "כפולה אפשרית" / "חיוב כרטיס אשראי"; עריכת שדות וקטגוריה; הסרה/בחירה; אישור או ביטול.
6. **שמירה:** `POST /api/imports` — טרנזקציה אחת: יצירת `imports` + כל העסקאות שנבחרו. כישלון = כלום לא נשמר.

### כפילויות
- **בתוך המסד:** `fingerprint` = hash של (תאריך, סכום באגורות, תיאור מנורמל, מזהה עסקה אם קיים). **השוואה לפי כמות:** אם בקובץ יש 2 עסקאות זהות ובמסד 1 — רק אחת מסומנת כחשודה (כי שתי קניות זהות באותו יום אפשריות).
- **אותו קובץ פעמיים:** לפי `file_hash` — אזהרה "הקובץ הזה יובא כבר ב-…".
- **בנק מול אשראי (ספירה כפולה):** שורות בדוח בנק שנראות כמו חיוב חודשי של כרטיס ("ישראכרט", "מקס", "כאל", "חיוב כרטיס"…) מסומנות "חיוב כרטיס אשראי — לא מיובא כברירת מחדל", והמשתמש מחליט. מוצג הסבר למה.
- הכפילויות **מוצגות** — לא נמחקות ולא מדולגות בשקט.

### היסטוריה וביטול
מסך "היסטוריית ייבוא" (קובץ, תאריך, כמה יובאו/נדחו/כפולים, סטטוס). **ביטול ייבוא:** מוחק רק עסקאות מאותו ייבוא שלא נערכו אחר כך; עסקאות שנערכו מוצגות ברשימה נפרדת והמשתמש מחליט עליהן. עם חלון אישור.

### מגבלות — בכנות
- **CSV/XLSX:** אמין, בכפוף לזיהוי כותרות; פורמט לא מוכר → התאמה ידנית.
- **PDF טקסטואלי:** אמין חלקית — תלוי בפריסת הדוח. ייבדק על כל פורמט בנפרד ויסומן "נתמך" רק אחרי בדיקה.
- **PDF סרוק (OCR):** **לא** בשלב הזה. אפשרי בעתיד עם tesseract.js בדפדפן (כמה MB, דיוק עברית בינוני) — רכיב נפרד, רק באישור.
- **AI חיצוני:** לא נעשה שימוש. אין שליחת דוחות לשום שירות.

## 7. סיכונים והחלטות (Risks & Decisions)

### סיכונים
| סיכון | הסבר | התמודדות |

| **דיוק פענוח דוחות** | כל בנק/חברת אשראי שונה; אין לי דוגמאות אמיתיות | התאמה ידנית, תצוגה מקדימה, דוגמאות מבנה ממך |

| **ספירה כפולה בנק/אשראי** | חיוב כרטיס בבנק = סכום העסקאות בדוח האשראי | סימון וברירת מחדל "לא לייבא" |

### החלטות שאני צריך ממך (עם המלצה)
1. **סדר העבודה:** עיצוב (B, C) קודם ואז אבטחה (D, E) — **מומלץ** (המסכים החדשים, כולל ההתחברות, ייבנו פעם אחת בשפה החדשה) / או אבטחה קודם.
2. **מיילים (אימות + שחזור סיסמה):** SMTP חיצוני חינמי (למשל Resend) — **מומלץ** / או בשלב ראשון בלי אימות מייל ובלי שחזור סיסמה.
3. **זיכויים והחזרים:** הוספת "סוג" לרשומה (הוצאה / זיכוי / הכנסה) — **מומלץ**, כדי שזיכוי לא ייספר כהוצאה / או לייבא הוצאות בלבד ולהציג זיכויים כ"לא מיובא".
4. **מטבע זר:** לשמור את סכום החיוב בש"ח (כפי שמופיע בדוח) + המטבע והסכום המקוריים כמידע — **מומלץ** / או לא לייבא עסקאות במטבע זר.
5. **קטגוריות:** להשאיר את 11 הקטגוריות הקיימות ולהוסיף סיווג אוטומטי אליהן — **מומלץ** / או לעבור לרשימה החדשה (מזון ומסעדות, קניות, תחבורה, חשבונות, בידור, בריאות, אחר) — זה משנה נתונים קיימים.
6. **דף "פילטרים":** לאחד אותו לתוך דף "הוצאות" (חיפוש + פילטרים בשורה) — **מומלץ** / או להשאיר דף נפרד.
7. **מנגנון הרשאות:** אפשרות א' (RLS דרך חיבור ישיר) — **מומלץ** / ב' (Data API + supabase-js) / ג' (סינון בקוד בלבד).
8. **פרסום:** האתר לא מתפרסם עד סוף E, ו-Milestone 6 הישן נבלע ב-H — **מומלץ**.
