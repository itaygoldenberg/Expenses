# Architecture

## 1. Technology Stack שנבחר

| רכיב | טכנולוגיה | תפקיד |
|------|-----------|-------|
| Frontend | React + TypeScript, נבנה עם Vite | כל מסכי האפליקציה, שרצים בדפדפן בטלפון ובמחשב |
| עיצוב | Tailwind CSS | עיצוב רספונסיבי עם תמיכה מלאה ב-RTL |
| ניווט בין מסכים | React Router | מעבר בין המסכים בתוך האפליקציה |
| גרפים | Recharts | גרף החלוקה לפי קטגוריות |
| קריאת קבצים | SheetJS (מההפצה הרשמית ב-cdn.sheetjs.com) | קריאת קובצי Excel ו-CSV בייבוא, בתוך הדפדפן |
| Database + התחברות | Supabase (PostgreSQL + Supabase Auth) | שמירת הנתונים בענן, סנכרון בין מכשירים, התחברות והגנה על הנתונים |
| בדיקות | Vitest | בדיקות אוטומטיות לחישובים ולחוקים העסקיים |
| Hosting | Vercel | פרסום האתר לאינטרנט ובנייה אוטומטית מ-GitHub |
| קוד המקור | Git Repository ב-GitHub | אחסון הקוד והיסטוריית הגרסאות |

### החלטות טכנולוגיות מרכזיות
- **אין Backend נפרד.** הדפדפן מדבר ישירות עם Supabase. את ההגנה על הנתונים מבטיחים חוקי הרשאה בתוך מסד הנתונים (Row Level Security), ולא קוד שרת. פעולות שחייבות לקרות "הכל או כלום", כמו מחיקת קטגוריה עם העברת הרישומים שלה, נכתבות כפונקציות בתוך מסד הנתונים. כך יש רכיב אחד פחות לבנות, לפרוס ולתחזק.
- **Supabase** נותן במקום אחד גם מסד נתונים בענן (שנדרש לסנכרון בין הטלפון למחשב) וגם התחברות. התוכנית החינמית מספיקה למשתמש אחד.
- **Vercel ולא GitHub Pages:** Vercel עובד בחינם גם עם repo פרטי, ובונה ומפרסם אוטומטית בכל דחיפה ל-GitHub. GitHub Pages בחינם דורש repo ציבורי.
- **React + Vite + TypeScript:** הכלים הנפוצים והמתועדים ביותר לאפליקציית דפדפן. TypeScript מונע טעויות בטיפוס הנתונים, למשל סכום שנשמר כטקסט.
- **קריאת קבצי הייבוא בתוך הדפדפן:** הקובץ מהבנק לא נשלח לשום שרת. רק העסקאות שהמשתמש אישר נשמרות במסד הנתונים.

### סיכונים ומגבלות
- **השהיית פרויקט ב-Supabase:** בתוכנית החינמית פרויקט בלי פעילות במשך כשבוע מושהה. הנתונים נשמרים, אבל צריך להפעיל אותו מחדש מלוח הבקרה של Supabase. בשימוש שוטף זה לא אמור לקרות.
- **מגבלות התוכנית החינמית של Supabase:** עד 2 פרויקטים פעילים, בדיוק מה שנדרש (Development ו-Production), ו-500MB למסד הנתונים, הרבה יותר ממה שמשתמש אחד צריך.
- **גיבוי:** לא מסתמכים על גיבויים אוטומטיים בתוכנית החינמית. אפשר לייצא את הטבלאות ידנית מלוח הבקרה של Supabase. בגרסה הזו אין באפליקציה עצמה פעולת ייצוא (ראה Out of Scope ב-PRD).
- **SheetJS:** הגרסה ב-npm ישנה ויש בה פרצת אבטחה ידועה. מתקינים רק מההפצה הרשמית (cdn.sheetjs.com) בגרסה עדכנית.
- **Vercel Hobby** מיועד לשימוש אישי ולא מסחרי, וזה מתאים למוצר הזה.
- **פורמטים של קבצי בנק משתנים בין בנקים.** לכן הייבוא מבוסס על התאמת עמודות ידנית ולא על תמיכה בבנק מסוים.

## 2. ארכיטקטורת המערכת

### מבנה המערכת
- **אפליקציית הדפדפן (Frontend):** כל המסכים והלוגיקה, כולל החישובים, קריאת קובצי הייבוא וזיהוי הכפילויות.
- **Supabase Auth:** התחברות עם אימייל וסיסמה למשתמש יחיד.
- **Supabase Database (PostgreSQL):** הטבלאות, חוקי ההרשאה (RLS) ופונקציות במסד הנתונים לפעולות שחייבות להיות אטומיות.

### Modules ושכבות
תיקיית `src/` מחולקת לפי יכולות:
- `features/auth`: התחברות והתנתקות.
- `features/transactions`: הוספה, עריכה, מחיקה ורשימת רישומים.
- `features/summary`: סיכום חודשי וגרף לפי קטגוריות.
- `features/categories`: ניהול קטגוריות.
- `features/recurring`: הוצאות קבועות.
- `features/import`: ייבוא קבצים.
- `lib/`: קוד משותף: חיבור ל-Supabase (`supabase.ts`), חישובי כסף (`money.ts`), חישובי תאריכים (`dates.ts`) וזיהוי כפילויות.

הלוגיקה העסקית (חישובים, תאריכים, כפילויות, פענוח קבצים) נכתבת כפונקציות טהורות ב-`lib/` או בתוך ה-feature, בנפרד מהמסכים, כדי שאפשר יהיה לבדוק אותה בבדיקות אוטומטיות.

### Frontend ו-Backend
- **Frontend:** אפליקציית עמוד יחיד (SPA). React Router מנהל את המסכים. מסכים פנימיים זמינים רק למשתמש מחובר, ומשתמש לא מחובר מועבר למסך ההתחברות.
- **Backend:** אין שרת נפרד. ה-"Backend" הוא Supabase: טבלאות, חוקי RLS ופונקציות SQL שהאפליקציה קוראת להן.

### Data Model
כל הטבלאות כוללות `user_id` (מקושר למשתמש ב-Supabase Auth), `created_at` ו-`updated_at`.

- **categories:** `id`, `name`, `kind` (`expense` או `income`).
  - שם ייחודי לכל משתמש ולכל סוג, בלי הבחנה בין אותיות גדולות לקטנות.
- **transactions:** `id`, `kind` (`expense` או `income`), `amount`, `date`, `category_id`, `recurring_id` (ריק אם לא נוצר מהוצאה קבועה), `recurring_month` (ריק אם לא נוצר מהוצאה קבועה).
  - `amount`: מסוג `numeric(12,2)`, חייב להיות גדול מאפס.
  - `date`: מסוג `date`, ללא שעה.
  - `category_id`: קטגוריה מאותו `kind`. אסור למחוק קטגוריה שיש לה רישומים בלי להעביר אותם קודם.
  - צירוף ייחודי של `recurring_id` + `recurring_month`: מבטיח שהוצאה קבועה תירשם פעם אחת בלבד בכל חודש, גם אם שני מכשירים פותחים את האפליקציה באותו רגע.
- **recurring_expenses:** `id`, `amount`, `category_id` (קטגוריית הוצאה), `day_of_month` (1–31), `start_date`, `active`.

**כסף:** סכומים נשמרים כ-`numeric` ולא כמספר עשרוני רגיל. בדפדפן החישובים נעשים באגורות, כמספרים שלמים, כדי למנוע טעויות עיגול.

**תאריכים:** "היום" ו"החודש הנוכחי" נקבעים לפי שעון ישראל (Asia/Jerusalem).

**קטגוריות התחלתיות:** כשהמשתמש נכנס בפעם הראשונה ואין לו אף קטגוריה, נוצרת לו הרשימה ההתחלתית. התוכן שלה ייקבע עם המשתמש לפני בניית ה-Milestone הרלוונטי.

### APIs ואינטגרציות
- **Supabase JS Client:** קריאה וכתיבה לטבלאות, והתחברות.
- **פונקציות במסד הנתונים (RPC):**
  - `generate_recurring_transactions()`: יוצרת את רישומי ההוצאות הקבועות שחסרים עד היום. נקראת בכל פתיחה של האפליקציה. בגלל האילוץ הייחודי, קריאה כפולה לא יוצרת כפילויות.
  - `delete_category(category_id, target_category_id)`: מעבירה את כל הרישומים וההוצאות הקבועות לקטגוריית היעד ומוחקת את הקטגוריה, בפעולה אחת.
- אין אינטגרציות חיצוניות נוספות. אין חיבור לבנקים.

### Data Flow
- **רישום ידני:** טופס ← בדיקת תקינות בדפדפן ← שמירה ב-Supabase (עם בדיקת תקינות נוספת במסד הנתונים) ← רענון הרשימה והסיכום.
- **סיכום חודשי:** שליפת רישומי החודש הנבחר ← חישוב בדפדפן של סך ההכנסות, סך ההוצאות, היתרה והחלוקה לפי קטגוריות.
- **הוצאות קבועות:** בפתיחת האפליקציה, אחרי התחברות ← `generate_recurring_transactions()` ← מסד הנתונים יוצר רישומים לכל חודש שבו הגיע יום החיוב ועדיין אין רישום. כך הרישום מופיע בתאריך הנכון גם אם האפליקציה לא נפתחה באותו יום.
- **ייבוא:** בחירת קובץ ← SheetJS קורא אותו בדפדפן ← המשתמש מתאים עמודות ← שליפת הרישומים הקיימים בטווח התאריכים של הקובץ ← סימון עסקאות עם אותו תאריך ואותו סכום כ"ייתכן שכפולה" ← המשתמש בוחר קטגוריות ומאשר ← שמירת העסקאות שאושרו בפעולה אחת.

### Authentication, Authorization, אבטחה ופרטיות
- **התחברות:** אימייל וסיסמה דרך Supabase Auth. המשתמש היחיד נוצר ידנית בלוח הבקרה של Supabase, והרשמה עצמית (Sign up) מבוטלת בשני הפרויקטים. כך אף אחד אחר לא יכול לפתוח חשבון.
- **הרשאות:** RLS מופעל בכל הטבלאות, עם חוק אחד: משתמש רואה ומשנה רק שורות שבהן `user_id` הוא שלו. פונקציות ה-RPC פועלות רק על הנתונים של המשתמש המחובר.
- **מפתחות:** בדפדפן משתמשים רק במפתח הציבורי של Supabase (anon / publishable key), שמותר לחשוף אותו כי RLS מגן על הנתונים. מפתח ה-service role לא נכנס לקוד ולא לדפדפן.
- **פרטיות:** קובצי הבנק נקראים בדפדפן בלבד ולא נשמרים בשום מקום. קבצים אמיתיים לא נשמרים בתיקיית הפרויקט. אם צריך קובץ לדוגמה לבדיקות, הוא מכיל נתונים בדויים בלבד.

### תשתיות, Hosting, Deployment ו-Configuration
- **קוד:** ב-GitHub (`itaygoldenberg/Expenses`).
- **פריסה:** Vercel מחובר ל-repo. כל דחיפה לענף `main` בונה ומפרסמת את האתר אוטומטית. קובץ `vercel.json` מפנה את כל הכתובות ל-`index.html`, כדי שרענון בתוך מסך פנימי לא יחזיר שגיאה.
- **סביבות:** שני פרויקטים נפרדים ב-Supabase:
  - **Development:** משמש לפיתוח ולבדיקות. המחשב המקומי מחובר אליו בלבד, דרך `.env`.
  - **Production:** האתר החי והנתונים האמיתיים. מחובר רק ל-Vercel, דרך Environment Variables שהמשתמש מגדיר בלוח הבקרה של Vercel.
- **משתני סביבה:** `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`. השמות מתועדים ב-`.env.example`, והערכים ממולאים על ידי המשתמש.
- **Database Migrations:**
  - כל שינוי במבנה מסד הנתונים נכתב כקובץ SQL בתיקייה `supabase/migrations/`, עם מספר ותיאור.
  - **Development:** Claude מריץ את ה-migration על פרויקט ה-Development (דרך Supabase CLI באמצעות `npx`, בלי Docker) ובודק שהוא עובד.
  - **Production:** רק לאחר אישור המשתמש. Claude מכין את ה-SQL, והמשתמש מריץ אותו ב-SQL Editor של פרויקט ה-Production בהדרכה צעד אחר צעד. זה קורה לפני הדחיפה שמפרסמת את הקוד שתלוי בו.
- **הגדרות שלא עוברות ב-migrations ויש להגדיר ידנית בכל פרויקט:**
  - ביטול הרשמה עצמית.
  - יצירת המשתמש.
  - כתובת האתר (Site URL) בהגדרות ה-Auth.

### החלטות טכניות מרכזיות נוספות
- **בדיקות אוטומטיות (Vitest)** לכל הלוגיקה שטעות בה שקטה ומסוכנת:
  - חישובי סכומים ויתרה.
  - חלוקה לפי קטגוריות ואחוזים.
  - חישוב תאריכי הוצאות קבועות (כולל יום 31 בחודש קצר).
  - פענוח קבצים וזיהוי כפילויות.
  - המסכים נבדקים ידנית מול ה-Definition of Done.
- **אין מצב עבודה ללא אינטרנט.** כשאין חיבור, פעולה נכשלת עם הודעה ברורה, ושום דבר לא נשמר בצורה חלקית.
- **רישום ראשון של הוצאה קבועה:** בתאריך החיוב הראשון שאינו לפני יום ההגדרה. לדוגמה, הוצאה קבועה ליום 1 שהוגדרה ב-15 לחודש תירשם לראשונה בחודש הבא.
